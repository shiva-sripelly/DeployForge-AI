# Architecture — Phase 1

This document records the design decisions behind the Phase 1 foundation and the reasoning
that later phases should preserve.

## Guiding decisions

| Decision | Rationale |
| --- | --- |
| Modular monolith (one API, one database) | The domain is still forming, so service boundaries would be guesses. Clear internal layers (api → services → models) keep a later extraction cheap. |
| Synchronous SQLAlchemy + psycopg 3 | Simple, well-understood transaction semantics. FastAPI runs sync endpoints in a threadpool. Async can be introduced per endpoint if profiling demands it. |
| Non-native enums (VARCHAR + CHECK) | New role or environment values need only a constraint change, not a PostgreSQL `ALTER TYPE`. Invalid values are still rejected by the database. |
| Deterministic constraint names | A metadata naming convention keeps migrations reviewable and makes constraint errors easy to trace. |
| App factory (`create_app(settings)`) | Tests build isolated app instances with their own settings, such as production mode or dev auth disabled. |
| Same-origin API in every environment | The Vite proxy (dev) and nginx (Docker) forward `/api`, so browsers never depend on CORS. CORS is still configured for split deployments. |

## Request lifecycle

1. **CORS middleware.** It is outermost, so error responses also carry CORS headers.
2. **Request-context middleware.** It assigns or propagates `X-Request-ID` (validated against
   a safe pattern), binds it to the logging context, adds security headers, logs one
   `request.completed` line with duration, and turns any unhandled exception into a generic 500
   envelope.
3. **Dependencies.** These resolve the settings, a request-scoped DB session, the
   authenticated user (`get_current_user`), and the request context used for auditing.
4. **Service call.** The service performs authorization checks and the business logic, writes
   audit events into the same session, and commits once.
5. **Exception handlers.** They map `AppError` subclasses, validation errors and HTTP errors to
   the shared error envelope.

## Data model

```
users ─┬─< organization_memberships >─┬─ organizations ─┬─< workspaces
       │        (org_id, user_id) UQ  │                 │     (org_id, slug) UQ
       │                │             │                 │     (id, org_id) UQ
       │                │             │                 │
       │                └──────(org_id, user_id)───┐    │
       │                                           ▼    ▼
       └──────────────────────────────────── workspace_memberships
                                              FK (workspace_id, org_id) → workspaces(id, org_id)
                                              FK (org_id, user_id)      → organization_memberships

audit_logs: organization_id?, workspace_id?, actor_user_id? (all ON DELETE SET NULL),
            action, resource_type, resource_id, details JSONB, request_id, ip, user_agent
```

- Every table uses UUID primary keys, generated by the application (`uuid4`) with a
  `gen_random_uuid()` server default as a fallback.
- `created_at` and `updated_at` are `timestamptz`, set by the database.
- `workspace_memberships.organization_id` is denormalized on purpose. Its two composite foreign
  keys make it **impossible at the database level** to:
  - attach a membership to a workspace in a different organization;
  - give workspace access to someone who is not a member of the organization.
- Removing someone from an organization cascades to all their workspace memberships in that
  organization.
- Every tenant-owned table carries `organization_id`. This prepares for PostgreSQL row-level
  security in Phase 2, where a policy keyed on a per-transaction `app.current_org` setting
  becomes a second line of defense behind the service-layer checks.

## Authorization

Authorization lives in [`app/services/authorization.py`](../backend/app/services/authorization.py).
Every check is a single join query that loads the resource together with the caller's
membership, so a separate fetch-then-check cannot race.

| Action | Owner | Admin | Member | Viewer | Non-member |
| --- | :-: | :-: | :-: | :-: | :-: |
| Read organization and stats | ✅ | ✅ | ✅ | ✅ | 404 |
| Read audit log | ✅ | ✅ | 403 | 403 | 404 |
| Create workspace | ✅ | ✅ | 403 | 403 | 404 |
| List workspaces | all | all | own | own | 404 |
| Read workspace and stats | ✅ | ✅ | if workspace member | if workspace member | 404 |

**404 vs 403.** If the caller cannot see a resource at all, the API answers 404, exactly as if
it did not exist. This prevents tenant enumeration. A 403 is returned only when the caller can
see the resource but their role does not allow the action, and the response lists the required
roles.

## Authentication (Phase 1)

- Access tokens are HS256 JWTs carrying `sub`, `iss`, `aud`, `iat`, `nbf`, `exp` and `jti`.
  Verification requires all of these claims and accepts only the configured algorithm, so
  `alg=none` and algorithm-confusion tokens are rejected.
- `POST /auth/dev/token` issues tokens for **existing, active** accounts only. It is mounted
  only when `DEV_AUTH_ENABLED=true`, and settings validation makes that impossible when
  `ENVIRONMENT=production`. Each issuance is audited.
- In Phase 2 an OIDC/SAML login flow replaces the dev endpoint. The token verification,
  `get_current_user` dependency and all authorization code stay unchanged.

## Observability

- Logs are one JSON object per line on stdout: timestamp, level, logger, message, request ID,
  and any structured `extra` fields. Set `LOG_FORMAT=console` for human-readable local output.
- `/health/live` is a process liveness check that touches no dependencies.
  `/health/ready` checks the database and returns 503 with per-component detail when a
  dependency is down. Docker health checks and the console's connectivity indicator use these.
- Every response carries `X-Request-ID`, which also appears in error bodies, logs and audit
  rows. This makes it possible to trace a user-visible error to the exact log lines.

## Frontend

- **Data fetching.** All server state goes through TanStack Query hooks in
  [`src/api/hooks.ts`](../frontend/src/api/hooks.ts). The client retries only network errors
  and 5xx responses, never 4xx.
- **Errors.** Axios errors are normalized into `ApiError`, which mirrors the backend envelope.
  A 401 clears the session and returns the user to sign-in. Validation errors (422) are mapped
  back onto form fields.
- **Design tokens.** Raw colors are defined once as CSS variables for light and dark mode in
  [`src/styles/index.css`](../frontend/src/styles/index.css). Tailwind's `@theme` exposes them
  as semantic utilities (`bg-surface`, `text-muted`, `border-border`), and components use only
  those utilities.
- **Accessibility.** Dialogs use the native `<dialog>` element (focus trap, Escape to close).
  Form fields wire up `aria-invalid` and `aria-describedby`, the API status indicator is a live
  region, there is a skip link, and the off-canvas navigation leaves the tab order when it is
  closed.
